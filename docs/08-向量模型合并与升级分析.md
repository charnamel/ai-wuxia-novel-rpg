# 向量模型合并与 bge-base 升级：技术分析与实施规范

> 状态：**分析稿（未实施）** ｜ 范围：`semantic_index.py`（世界书语义层）与 `local_vector_store.py`（记忆库向量层）
> 结论一句话：合并本身不会引入逻辑错误（向量语义 / 维度 / 状态均安全），真正的风险集中在**"加载是否阻塞"**与**"编码是否上锁"**两个实现选择上。
> 修订：2026-09-19 代码复核后修正 4 处（检索阻塞实际依赖调用方门控、重建原子性仅记忆库成立、回滚缺少备份步骤、"无报错提示"表述不准），新增 §5.5 快照语义与重试退避规范。

## 1. 背景

### 1.1 现状：两套向量检索并存

| 子系统 | 模块 | 模型（默认） | 向量文件 | 条目数 × 维度 | 查询阈值 |
|---|---|---|---|---|---|
| 世界书语义层（L5） | `semantic_index.py` | `SEMANTIC_MODEL` = `BAAI/bge-small-zh-v1.5` | `data/semantic_vectors.npy` | **2242 × 512** | `SEMANTIC_MIN_SIMILARITY=0.45`，权重 `×2.0` |
| 记忆库向量层 | `local_vector_store.py` | `LOCAL_MEMORY_MODEL`（.env 现为空 → 代码 fallback 到 small） | `data/local_memory_vectors.npy` | **4923 × 512** | `min_score=0.40~0.45` |

两者是**同名的两个独立实例**（`sentence_transformers.SentenceTransformer(name, device='cpu')` 各构造一次）。

> 注：表中条目数（2242 / 4923）为本文写作时点的快照，随游戏进行持续增长；重建耗时与向量体积应按升级当天的实际条目数重估。

### 1.2 当初为何设计成两个实例（代码原文）

```
local_vector_store.py:7-8
  【模型】独立加载 BAAI/bge-small-zh-v1.5（与世界书 semantic_index.py 互不干扰，
         各自一个模型实例，故障隔离 + 主动检索线程可真并行）
```

归纳为四条：

1. **故障隔离**：两边失败模式不同 —— 世界书是*惰性加载 + 可降级为纯关键词*；记忆库是*启动预热 + 10 次重试 + 未就绪返回空*。共用实例即共用命运。
2. **并发**：主动检索每轮开后台线程与主流程并发，两个实例各编各的，不抢同一把锁。
3. **可各配不同模型**：因此才有两个独立 env（`SEMANTIC_MODEL` / `LOCAL_MEMORY_MODEL`）。
4. **出身不同**：记忆库用于替换百炼云向量库（要求 API 完全一致、`MEMORY_BACKEND=local` 路由切换），需要自包含；世界书语义层则跟随 worldbook 索引生命周期。

### 2.2 检索链路

**世界书四路打分**（`worldbook.py:872-884` 接入 L5；最终阈值 `_SCORE_THRESHOLD=1.5` + 每类槽位 + `_DEFAULT_MAX_CHARS=3000` 预算截断）：

| 路 | 机制 | 权重 |
|---|---|---|
| L1 | 精确命中标题/人名 | +10 |
| L2 | 条目 keywords 命中 | +1 / 词 |
| L3 | gram 模糊匹配 | 0.05 ~ 0.3（按类别） |
| **L5** | `bge-small` 向量余弦 ≥ 0.45，取 top30 | **× 2.0** |

**记忆库检索**（`get_relevant_history()` `:604-611` → `search()`）：
```
候选集(前置过滤：user_id / category / entity)
  → query 编码 → 相似度 = 归一化向量内积
  → 门槛 min_score 过滤
  → 排序分 = 相似度 + 活跃/新近奖励 + 专名关键词奖励
  → top_k → 格式化文本
```

### 2.3 配置项（最易踩的坑）

```ini
# .env
ENABLE_SEMANTIC_SEARCH=true
SEMANTIC_MODEL=BAAI/bge-small-zh-v1.5        # ← 世界书语义层
SEMANTIC_MIN_SIMILARITY=0.45
SEMANTIC_SCORE_WEIGHT=2.0

```
**只改其中一个 = 两库使用不同模型**（世界书 768 维、记忆库 512 维）→ 一半检索失效。

### 2.4 与云后端的关系

`local_vector_store` 是 `cloud_memory_v2` 的 drop-in（函数名/参数/返回格式一致），由 `MEMORY_BACKEND=local` 路由切换；服务器现为纯本地（百炼不计费）。

## 4. 风险分析

### 4.1 高危三项

#### BUG-1（严重）：请求路径阻塞等待共享模型 → gunicorn worker 超时死循环

- **机制**：两边代码把"检索路径绝不等待模型"写为铁律：
  ```
  local_vector_store.py:221  调用方：后台预热线程/写入线程/重建接口。检索路径绝不调用本方法（防请求超时拖死worker）
  semantic_index.py:88       【铁律】请求路径绝不等待模型加载（服务器上30-60秒会拖死gunicorn worker）
  ```
- **触发**：合并后用单一"阻塞式 `get_model()`"，且检索路径（`search_semantic` / `_encode`）调用它。
- **后果**：重启后第一次检索卡 30~60s → worker 被杀 → 新 worker 重新加载 → 再卡 → **死循环**（表现为"游戏卡住必须刷新"）。
- **规范**：工厂必须提供**双 API**：`get_model_nowait()`（检索路径；绝不等待，可踢后台加载）+ `ensure_loaded()`（仅预热/写入/重建）。

#### BUG-2（严重）：给"编码"加全局锁 → 重建/加载期间检索被阻塞数分钟

- **机制**：现状编码不持锁（`:259-271` 仅做 `self._model` 快照 + 分块循环）；两实例各编各的，唯一代价是 CPU 争用。
- **触发**：合并时出于"线程安全"直觉，在共享封装上加全局锁；而 `rebuild_vectors()` 会一次传入 ~4900 条（`:678`）执行长时间编码，模型加载本身也是 30~60s 单次调用。
- **后果**：主线程的世界书语义检索（每轮都跑）排队等待 → 单轮延迟达分钟级 → 同样触发 worker 超时。
- **规范**：**不要给 encode 加全局锁**（`SentenceTransformer.encode` 在 CPU 上并发安全：`eval()` 幂等、`normalize` 无副作用、推理释放 GIL）；若需保险，采用**分块锁（≤64 条/次）**。

#### BUG-3（中等）：失败/重试策略"就低"统一 → 丢失自愈

| | `semantic_index` | `local_vector_store` |
|---|---|---|
| 失败后 | **不再重试**（`_model_load_started` 一次） | `_MODEL_ERROR_TTL=60`（`:55`）超时解冻 + 预热 `10×15s`（`:485-507`） |

- **触发**：合并时采用"一次失败即冻结"策略。
- **后果**：在"服务器重启瞬间的内存竞争"这类一过性故障下，**两条检索线一起死到下次重启**（记忆库现在能自愈）。
- **规范**：采用记忆库的 **TTL 冻结 + 后台重试** 作为共享策略。

### 4.2 低危与提示项

| # | 项 | 说明 | 规范 |
|---|---|---|---|
| BUG-4 | 并发 encode 的正确性 | ST 推理无状态；并发 CPU 编码结果正确，仅 CPU 争用（2 核） | 无需处理；若引入锁反而降低并发（现注释已声明"真并行"） |
| BUG-5 | 首载峰值 | 见 §3（合并后为**收益**） | 工厂内**加载锁**保证同一模型只加载一次 |
| BUG-6 | 锁顺序 | 记忆库持 `self._model_lock` 时请求工厂锁（store→factory 单向）；世界书仅取工厂锁 | 工厂**不得回调**任何 store 内部方法（保持单向） |
| BUG-7 | 异名模型 | `SEMANTIC_MODEL ≠ LOCAL_MEMORY_MODEL` 时工厂按名加载两份（与今天一致） | 工厂按**模型名**缓存；无收益但不报错 |
| BUG-8 | `_ENABLE=false` 时模型仍被加载 | 记忆库需要模型 → 世界书显示"未启用"但模型在内存 | 属正常行为（世界书不会误用：`is_available()` `:91-92` 直接 False） |
| BUG-9 | 重建期 CPU 争用 | 重建满载会拖慢所有检索（与是否共享无关） | 建议非游戏时段执行 |

### 4.3 已核实"不会出问题"的点

| 点 | 证据 |
|---|---|
| 向量语义一致（分数不会错乱） | 两边均 `normalize_embeddings=True`（`local:269` / `semantic:242,322`）→ 内积=余弦，口径不变 |
| 无模型属性被改写（不会串味） | 全项目检索：**无** `max_seq_length` / `.half()` / `.to(device)` / `set_num_threads` 赋值 |
| 维度动态取值 | `semantic_index.py:356` `vector_dim = _vectors.shape[1]`；记忆库同理 → 512/768 无关宏旨 |
| 状态展示不受影响 | `/worldbook/status`、`/memory/status` 均读模块自身状态 |
| 重建原子性 | **仅记忆库成立**：`rebuild_vectors()` 在数据锁内原子替换（`:691-711`）。⚠️ 世界书侧 `build_vectors()` **无锁多步**（`:249-257` 先 vstack `_vectors`、再 append `_id_list`，两步之间检索并发会读到"新向量+旧ID"的短暂错位）；低频重建下风险低，合并不动此处即维持现状 |

## 5. 安全实现规范

### 5.1 目标架构

```
        ┌──────────────────────── embedding_registry (新增, ~30 行) ───────────────────────┐
        │  按模型名缓存实例：{name: {model, loading, error, error_at, load_lock}}           │
        │  ① get_model_nowait(name)  → 就绪返回 model；未就绪返回 None（可踢后台加载）      │
        │  ② ensure_loaded(name)     → 阻塞加载（仅预热/写入/重建调用）                     │
        │  ③ 失败策略：TTL 冻结 + 可重试（沿用 local_vector_store 现行策略）               │
        │  ④ encode 不加全局锁（或提供 chunked_encode 分块锁版本）                          │
        └───────────────┬───────────────────────────────────────────┬──────────────────────┘
                        │                                           │
        semantic_index（惰性 + _ENABLE 开关）          local_vector_store（预热线程 + TTL 重试）
```

### 5.2 接口草案（伪代码）

```python
# embedding_registry.py
_LOCK = threading.Lock()
_SLOTS = {}          # name -> {"model":…, "loading":bool, "error":str, "error_at":float, "load_lock":Lock}
_ERROR_TTL = 60      # 秒：失败冻结期（与 local_vector_store._MODEL_ERROR_TTL 对齐）

def get_model_nowait(name):
    """检索路径专用：绝不阻塞。未就绪时（可选）踢一次后台加载，返回 None。"""
    slot = _SLOTS.setdefault(name, _new_slot())
    if slot["model"] is not None:
        return slot["model"]
    if slot["loading"]:
        return None
    if slot["error"] and (time.time() - slot["error_at"]) < _ERROR_TTL:
        return None
    _kick_background_load(name, slot)   # 与 semantic_index.is_available() 同款行为
    return None

def ensure_loaded(name):
    """仅预热/写入/重建调用：阻塞加载（带双检锁 + TTL 解冻）。"""
    ...
```

### 5.3 改动点（最小侵入）

| 文件 | 改动 |
|---|---|
| `semantic_index.py` | `_load_model()` 内部改为 `embedding_registry.ensure_loaded(_MODEL_NAME)`；`is_available()` 改为 `embedding_registry.get_model_nowait(...) is not None`；⚠️ **红线**：`search_semantic():315` 的阻塞式 `_load_model()` **必须**换成 `get_model_nowait()`（未就绪直接返回 `[]`）——现状靠 worldbook 门控兜底，合并后不可再依赖调用方，漏改这一行即触发 BUG-1 死循环 |
| `local_vector_store.py` | `_load_model()` 内部改为 `ensure_loaded`；`_encode()` 的 `model = self._model` 改为 `get_model_nowait(_MODEL_NAME)`（未就绪返回 None 的语义保持不变）；预热线程照旧 |
| `.env` | 建议两处同名（详见 §8） |

> 其余逻辑（降级、预热重试、重建、统计、阈值）**全部不动**。

### 5.4 四条硬性规范

1. **双 API**：检索路径只允许 `get_model_nowait`；`ensure_loaded` 仅限预热/写入/重建。
2. **编码不加全局锁**（或分块锁 ≤64 条/次），避免重建阻塞检索。
3. **失败策略**：TTL 60s 冻结 + 后台重试（沿用记忆库）。
4. **按模型名缓存**：同名共享、异名各自（保留双 env 灵活性）。
5. **重试退避**：TTL 自愈须防"重试风暴"——1.9G 内存机器上若 base 因内存不足加载失败，每 60s 解冻重试一次 30-60s 的加载会形成周期性内存抖动。工厂对**连续失败**做退避（如连续 3 次失败后间隔翻倍、封顶 10 分钟），任一次成功即清零计数。

### 5.5 快照语义：合并后仍沿用的取用方式

两个模块现状的"快照"模式在合并后**原样保留**——这正是合并可行的根基（§5 的工厂本质就是"共享实例 + 快照取用"）：

- **取模型 = 取引用快照**：`model = get_model_nowait(name)` 是一次原子引用读取（GIL 保证无撕裂读）；就绪拿到对象，未就绪拿到 `None`，**绝不等待**。
- **旧快照可安全用完**：模型因失败被卸载重载时，已持有旧引用的线程会把旧对象用完再交给 GC，不会中途失效、无需加锁保护。
- **向量矩阵照旧各自快照**：记忆库在数据锁内快照 `sub_matrix` / `entries_snapshot`（`:422-423`）；世界书侧维持现状（原子性差异见 §4.3）。
- **代价（必须知晓）**：①可用性共命运——加载窗口内两条检索线一起降级（现状各自独立）；②模型快照与向量快照之间**没有**版本一致性保证，靠"按模型名缓存 + 换模型必重建向量"的纪律兜底；③实施 §5.2 伪代码时，`_SLOTS` 的读改写（setdefault / loading 标记）须在 `_LOCK` 内完成，仅 `slot["model"]` 的单次读取可无锁。

| 2 | 重建不阻塞检索 | 一边 `POST /memory/rebuild`，一边循环触发一次世界书检索并计时 | 延迟只受 CPU 影响，**无秒级以上的锁等待** |
| 3 | 重启首轮不卡 | 重启后立刻发一轮请求，检查日志 | 请求线程未被阻塞；无 gunicorn worker timeout；模型就绪后记忆检索自动恢复 |
| 4 | 内存对比 | 合并前后 `ps -o rss`（worker） | base 场景应减少约 300~400MB |
| 5 | 自愈验证 | 临时把模型名改为不存在的名字 → **重启**（.env 改动需重启进程才生效）→ 等待 > TTL → 改回 → 再重启 | TTL 后自动重试并恢复（不会被永久冻结） |

## 7. 回滚方案

1. `git revert`（或还原）合并相关改动；
2. 无需回滚向量文件（合并不改向量）；
3. 重启服务即可恢复双实例行为。

（若连同 bge-base 升级一起回滚，见 §8.5 步骤 0 + 回滚步骤。）

## 8. 附：升级 bge-base 的连带事项

### 8.1 维度变化与两套向量重建

| 项 | 值 |
|---|---|
| 维度 | bge-small **512** → bge-base **768** |
| 旧向量后果 | 维度不符 → `sub_matrix @ qv.T` 抛错 → `get_relevant_history:629-635` 捕获后返回空 → **运行时静默降级**（并非完全无提示：启动时 meta 模型校验 `:184-186` 会警告"向量由 X 生成，当前配置 Y"；每次检索失败 `:634` 打印原因；但游戏侧无感、不报错） |
| 必须重建 | `POST /worldbook/rebuild`（2242 条） + `POST /memory/rebuild`（4923 条） |
| 预计耗时 | 2 vCPU、base 模型约 **5~8 分钟**（建议非游戏时段） |
| 向量体积 | 记忆库 9.7MB → ≈14.5MB；世界书 4.4MB → ≈6.6MB（无影响） |
| ⚠️ env 同改 | `SEMANTIC_MODEL` 与 `LOCAL_MEMORY_MODEL` 必须**同时**改为 base；后者留空会 fallback 回 small → 双实例回归（内存翻倍 + 两库维度不齐） |
| ⚠️ 升级前备份 | **必须**先做 §8.5 步骤 0 的备份（`.env` + 两份 `.npy`），漏做则向量无法回滚 |

### 8.2 服务器资源现状与预算（实测）

| 项 | 实测值 |
|---|---|
| 内存 | total **1.9Gi** / available ≈ 640~666Mi / **swap 1.0Gi（已用 107Mi）** |
| CPU | 2 vCPU |
| 当前 worker RSS | **929MB**（bge-small + 4923 向量） |
| bge-base 模型缓存 | **已就绪**：`~/.cache/huggingface/hub/models--BAAI--bge-base-zh-v1.5`（781MB，含 safetensors 与 pytorch_model.bin 两格式） |
| 磁盘 | 40G，已用 20G（余量充足） |

结论：**必须先合并实例再上 base**；否则 2 × ~400MB 模型权重 + torch 运行时 ≈ 极可能 OOM。合并后：模型权重 400MB（单份）+ 运行时常量 ≈ 峰值可控，swap 作为保险。

### 8.3 离线加载

systemd 单元含 `Environment=HF_HUB_OFFLINE=1` 与 `HF_ENDPOINT=https://hf-mirror.com`。
因模型已缓存，**离线可直接加载**；若需重新下载，须临时 `HF_HUB_OFFLINE=0` 并保持镜像源。

### 8.4 阈值复校（换模型后必做）

换模型后相似度分布会变化，需用同一批查询对比后微调：
- 世界书：`SEMANTIC_MIN_SIMILARITY`（现 0.45）、`SEMANTIC_SCORE_WEIGHT`（现 2.0）
- 记忆库：检索调用的 `min_score`（现 0.40~0.45）
（建议方法：固定 3~5 组真实查询，打印 top-5 的分数与内容，人工判断相关/噪声的分界。）

### 8.5 升级前备份与回滚步骤

**步骤 0（升级前必做，回滚依赖，漏做则向量无法回滚）**：

```bash
cp .env                           .env.bak_small
cp data/local_memory_vectors.npy  data/local_memory_vectors.npy.bak_small
cp data/semantic_vectors.npy      data/semantic_vectors.npy.bak_small
```

**回滚**：

```bash
# 1) 还原配置（从步骤 0 的备份恢复，内容为 small 双同名）
cp .env.bak_small .env
# 2) 还原向量（从步骤 0 的备份恢复）
cp data/local_memory_vectors.npy.bak_small data/local_memory_vectors.npy
cp data/semantic_vectors.npy.bak_small      data/semantic_vectors.npy
# （可选）rm data/local_memory_meta.json —— 回滚后其 model 字段仍是 base，
#   会触发一次无害的启动警告；下次落盘会自动改写
# 3) 重启
sudo systemctl restart game1
```

### 8.6 常见误区

- **BGE v1.5 不需要查询指令前缀**：v1.5 的设计目标之一就是"无需 instruction 亦可获得合理相似度分布"，因此代码中**不应**添加"为这个句子生成表示以用于检索相关文章："（那是 v1.0 的用法）。
- 换模型**不需要**改动检索算法：维度为动态取值，评分公式与门槛机制均与模型无关。
