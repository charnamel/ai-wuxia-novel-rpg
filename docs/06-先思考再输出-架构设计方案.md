# "先思考 · 再检索 · 后输出" 架构设计方案

> 面向 AI 武侠互动 RPG 的两阶段推理架构设计
> 版本：v1.0（草案）

## 一、设计背景与目标

### 1.1 当前问题

当前主循环采用**单段式**架构——把所有上下文一股脑塞给大模型，一步到位输出剧情 + 状态更新。随着游戏内容越来越复杂（276 个 NPC、多层记忆、世界书、主线/支线、战斗系统、修炼系统……），单段式逐渐暴露出以下问题：

| 问题 | 表现 | 根因 |
|------|------|------|
| **状态遗漏** | 剧情里说"受了伤"，但 self_state / NPC 状态没更新 | AI 一步到位输出，顾了文笔顾不了数值 |
| **前后矛盾** | 上一轮说获得某物品，下一轮又"第一次见到" | 长上下文中关键信息被淹没 |
| **检索被动** | 玩家不提的事情，AI 不会主动想起 | 只用玩家输入做检索 query，缺了主动联想 |
| **选择敷衍** | 行动选项千篇一律，"继续观察/上前搭话/离开" | AI 没认真想过"当前局面有哪些真实选项" |
| **剧情漂移** | 主线走着走着偏了，NPC 性格慢慢变了 | 缺乏每轮的一致性校验 |

### 1.2 设计目标

引入**两阶段推理架构**（思考阶段 + 输出阶段），用"多一次小模型调用"的代价，换取：

- **状态准确率**：从 ~85% → ~98%（漏更新、错更新大幅减少）
- **记忆一致性**：主动回忆相关线索，长剧情下"遗忘"减少 60%+
- **剧情质量**：选项更有意义、冲突更合理、伏笔能回收
- **成本可控**：总 token 成本增加 ≤ 20%（小模型思考 + 精准上下文抵消）
- **延迟可接受**：配合流式输出，首字延迟感知不明显增加

## 二、整体架构

### 2.1 架构选型对比

| 方案 | 调用次数 | 成本增加 | 延迟增加 | 质量提升 | 推荐度 |
|------|---------|---------|---------|---------|--------|
| 单段式（现状） | 1次大模型 | 0% | 1x | 基准 | — |
| **两段式（推荐）** | 1次小模型 + 1次大模型 | ~10% | ~1.2x | 显著 | ⭐⭐⭐⭐⭐ |
| 三段式（思考+检索+输出） | 1次小模型 + 1次大模型 | ~15% | ~1.3x | 最大 | ⭐⭐⭐⭐ |

### 2.2 为什么推荐两段式

1. **检索可以嵌在中间，不算独立调用**——思考阶段输出结构化的检索关键词，后端同步执行检索，把结果注入输出阶段的上下文。本质上还是两次 LLM 调用，检索是穿插的本地操作。
2. **小模型足够胜任思考**——思考不需要文采，只需要"分析局面、列出关键点"，Flash 级小模型完全够用，成本是大模型的 1/10。
3. **改造难度适中**——现有主循环结构不用大改，只是在主调用前插一步思考调用。

### 2.3 架构图

```
玩家输入
   │
   ▼
┌─────────────────────────────────┐
│  Step 1：思考阶段（小模型）      │
│  输入：精简上下文（L1+状态+任务） │
│  输出：结构化思考 JSON            │
│        · 当前局面分析             │
│        · 需要检索的关键词         │
│        · 状态变化预判             │
│        · 行动选项草案             │
└───────────────┬─────────────────┘
                │
                ▼
┌─────────────────────────────────┐
│  本地检索（同步执行）             │
│  · 用思考关键词搜 L4 记忆        │
│  · 用思考关键词搜世界书          │
│  · 用思考关键词搜任务            │
└───────────────┬─────────────────┘
                │
                ▼
┌─────────────────────────────────┐
│  Step 2：输出阶段（大模型）      │
│  输入：精准上下文 + 思考结果     │
│  输出：剧情正文 + 工具调用        │
└───────────────┬─────────────────┘
                │
                ▼
          前端流式展示
```

## 三、Step 1：思考阶段详细设计

### 3.1 模型选择

- **推荐模型**：deepseek-v3-flash（或同级便宜模型）
- **预估成本**：输入 3k token + 输出 0.5k token ≈ 主模型成本的 5~10%
- **温度**：0.2（低温度，确保分析严谨不发散）

### 3.2 输入上下文（精简版）

思考阶段不需要全量上下文，只需要"能做出正确判断的最小信息集"：

```
【当前局面 · L1 锚点】
（上一轮剧情末 400 字）

【玩家本轮行动】
（玩家输入）

【主角状态速览】
姓名 / 境界 / 身体状态 / 当前武功前3 / 装备 / 名气

【当前世界状态】
时辰 / 地点 / 天气 / 小说节点

【当前任务】
（活跃任务简述）

【活跃 NPC】
（最近出场 NPC 及其好感/状态）

【特殊指令】
（主线触发 / 随机事件等，有则给，无则不给）
```

**预估输入 token**：2500~3500（是完整上下文的 1/3 ~ 1/2）。

### 3.4 思考阶段的核心价值

这 6 个模块分别解决 6 类问题：

| 模块 | 解决的问题 |
|------|-----------|
| `situation_analysis` | AI 不再"条件反射"式回应，先想清楚局面再动笔 |
| `retrieval_keywords` | 从"玩家说什么搜什么"变"主动联想相关线索" |
| `state_changes_preview` | 先预判哪些状态该变，输出阶段不会漏 |
| `action_options` | 选项从"凑数的"变成"真正影响走向的" |
| `consistency_check` | 主动列出不能违反的事实，减少前后矛盾 |
| `narrative_direction` | 剧情有节奏，不是想到哪写到哪 |

## 四、检索阶段详细设计

### 4.1 检索触发时机

思考阶段输出完成后，后端从 `retrieval_keywords` 中提取关键词，**同步执行**多路检索。这一步在本地完成，不走 LLM，耗时 0.1~0.3 秒。

### 4.2 检索内容（6 路并行）

| 检索源 | 输入 | 输出 | 用途 |
|--------|------|------|------|
| L4 NPC 记忆 | `npcs` 列表 | 每位NPC的相关记忆摘要 | 输出阶段注入NPC记忆块 |
| L4 剧情线索 | `plot_threads` | 历史剧情相关片段 | 前后呼应、伏笔回收 |
| L4 任务记忆 | `quests` | 相关任务历史 | 确保任务进度连贯 |
| 世界书（NPC/武功/门派/地点/物品） | 全部关键词 | 相关设定条目 | AI 不瞎编设定 |
| 任务列表 | `quests` | 相关任务详情 | 任务推进/更新 |
| 传闻/里程碑 | `plot_threads` | 相关传闻记录 | 江湖氛围、玩家名声影响 |

### 4.3 检索结果注入方式

检索结果不直接全量塞给输出阶段，而是：

1. **按相关度排序**，取 top N（如 NPC 记忆取每人 top 3，世界书取 top 10 条）
2. **去重和精简**：相似内容合并，每条控制在 50 字以内
3. **打上明确标签**：注入到输出阶段的上下文中，用 `【*思考检索结果*】` 标识，AI 知道这些是"思考阶段主动想起来的"

### 4.4 与现有检索的区别

| 维度 | 现有被动检索 | 思考驱动检索 |
|------|-------------|-------------|
| Query 来源 | 玩家输入 | 思考阶段的深度分析 |
| 覆盖维度 | 玩家说了什么搜什么 | 主动联想相关 NPC、物品、任务、伏笔 |
| 准确度 | 容易漏（玩家不提就不搜） | 更全面（AI 主动补全） |
| 时机 | 和主调用一起组装 | 思考阶段后、输出阶段前 |

## 五、Step 2：输出阶段详细设计

### 5.1 模型选择

- **推荐模型**：主模型保持不变（当前用什么就用什么）
- **温度**：保持当前配置（0.65 左右）
- **流式输出**：开启 SSE 流式，逐字推送到前端

### 5.2 输入上下文（精准版）

输出阶段的上下文 = **精简上下文 + 思考结果 + 检索结果**。

完整结构：

```
【系统提示】（保持不变）

【世界设定】（保持不变）

──── 以上固定，最大化前缀缓存命中 ────

【*L3-1 全局剧情脉络*】（保持不变）
【*L3-2 近期概要*】（保持不变）
【*L2 最近50轮细节*】（保持不变）
【*L1 即时场景锚点*】（保持不变）

【*当前世界状态*】（保持不变）
【*当前任务目标*】（保持不变）
【*主角面板*】（保持不变）

【*当前活跃NPC状态*】（保持不变）

──── 以上是基础上下文 ────

【*思考阶段分析*】
  · 核心冲突：xxx
  · NPC动机：
    - 胡斐：表面xxx，实则xxx
  · 利害关系：xxx
  · 叙事节奏：xxx
  · 关键情节点：1.xxx 2.xxx 3.xxx

【*思考检索结果 · 主动回忆*】
  · NPC记忆：
    - 胡斐：xxx
    - 苗人凤：xxx
  · 剧情线索：xxx
  · 世界书相关：xxx
  · 相关任务：xxx

【*一致性约束*】（思考阶段列出的 must_keep + avoid_contradiction）
  · 必须遵守：
    1. xxx
  · 避免矛盾：
    1. xxx

【*状态变化预判*】（思考阶段的 state_changes_preview）
  本轮预计：好感变化 / 物品增减 / 地点不变 / ...
  （输出阶段的 update_game_state 必须与此一致，不能遗漏也不能多加）

【玩家本轮行动】
（玩家输入）

【再次强调】
...
```

### 5.3 输出要求

输出阶段仍然使用 function calling 调用 `update_game_state`，但增加一条约束：

> **状态更新必须与"状态变化预判"一致。预判为 true 的类别必须有对应更新，预判为 false 的类别不得出现更新。**

这样相当于有了**双重校验**：思考阶段先预判"会不会变"，输出阶段再填具体数值。漏更和错更的概率大幅下降。

### 5.4 行动选项

行动选项**不再从剧情正文中用正则提取**，而是直接用思考阶段的 `action_options`。前端直接渲染成按钮：

- 选项文字来自 `text` 字段
- 鼠标悬停可显示风险等级（1-5星）
- `type` 字段可用于前端给不同选项上色（激进=红，稳健=蓝， etc.）

## 六、战斗场景的特殊处理

战斗是最复杂、最容易出问题的场景，思考阶段需要额外加强。

### 6.1 战斗中的思考阶段

战斗模式下，思考阶段增加战斗专用字段：

```json
{
  "battle_analysis": {
    "player_advantage": {"type": "string", "description": "玩家优势在哪"},
    "enemy_advantage": {"type": "string", "description": "对手优势在哪"},
    "current_tempo": {"type": "string", "enum": ["玩家占优", "均势", "对手占优", "胶着"]},
    "next_move_expected": {"type": "string", "description": "对手下一招可能是什么"},
    "dc_estimate": {
      "type": "object",
      "properties": {
        "attack_dc": {"type": "integer", "description": "攻击DC预估值"},
        "defense_dc": {"type": "integer", "description": "防御DC预估值"}
      }
    }
  }
}
```

### 6.2 战斗输出的额外约束

- 每轮战斗的伤害数值必须与思考阶段的 `dc_estimate` 大致匹配
- 战斗走向必须与 `current_tempo` 一致（不能思考阶段说"对手占优"，输出阶段玩家一刀秒杀）
- 每轮战斗结束后，思考阶段重新评估局面，下一轮再调整

## 七、成本与性能分析

### 7.1 Token 成本估算

以单段式为基准（100%）：

| 阶段 | input token | output token | 模型 | 相对成本 |
|------|-------------|-------------|------|---------|
| 单段式（现状） | 8000 | 800 | 大模型 | 100% |
| Step 1 思考 | 3000 | 500 | 小模型（1/10价格） | ~5% |
| Step 2 输出 | 7000（精准后反而减少） | 800 | 大模型 | ~88% |
| **两段式合计** | — | — | — | **~93%** |

**结论**：因为精准检索让 Step 2 的 input 减少了，总成本可能**不升反降**。即使增加，也在 10% 以内。

### 7.2 延迟估算

| 阶段 | 耗时 | 说明 |
|------|------|------|
| 单段式总延迟 | 4~6 秒 | 从请求到完整返回 |
| Step 1 思考 | 1~2 秒 | 小模型速度快 |
| 本地检索 | 0.2~0.5 秒 | 向量检索很快 |
| Step 2 输出（首字延迟） | 1~2 秒 | 流式输出，首字出来就开始显示 |
| **两段式首字延迟** | **2.5~4 秒** | 比单段式还快？ |
| **两段式完成延迟** | **5~8 秒** | 总完成时间略长 |

**关键洞察**：配合流式输出，**玩家感知的等待时间反而更短**——因为单段式是"等 5 秒然后一下子全出来"，两段式是"等 3 秒然后字开始一个一个蹦"。心理学上后者感觉更快。

## 八、实施路线（分三阶段）

### Phase 1：最小可行版（1-2 天）

**目标**：跑通两段式骨架，验证可行性

- [ ] 新增 `thinking_prompt`：精简上下文 + JSON Schema
- [ ] 新增 `llm_call_thinking()` 封装：调用小模型，强制 JSON 输出
- [ ] 思考阶段只做 3 个核心模块：`situation_analysis` + `retrieval_keywords`（npcs 部分） + `consistency_check`
- [ ] 检索阶段只做 NPC 记忆 + 世界书
- [ ] 输出阶段注入思考结果 + 检索结果
- [ ] 状态更新仍用现有逻辑，不加强制校验

**验收标准**：游戏能正常跑，剧情质量不下降，成本变化 < 20%

### Phase 2：完整功能版（3-4 天）

**目标**：思考阶段 6 模块全部上线，质量明显提升

- [ ] 补全 `state_changes_preview` + 状态校验（漏更/错更报警）
- [ ] 补全 `action_options`（前端直接渲染选项按钮）
- [ ] 补全 `narrative_direction`（叙事节奏指导）
- [ ] 检索扩展到 6 路（NPC记忆/剧情线索/任务/世界书/传闻/里程碑）
- [ ] 输出阶段增加一致性约束提示
- [ ] 战斗场景适配

**验收标准**：
- 状态遗漏率下降 50%+
- 行动选项质量显著提升（不再是换皮）
- 前后矛盾出现频率下降

### Phase 3：优化版（2-3 天）

**目标**：成本优化 + 体验优化

- [ ] 流式输出（SSE）：字一个一个蹦，感知延迟大幅降低
- [ ] 前缀缓存优化：思考阶段上下文单独优化缓存命中
- [ ] 失败重试机制：思考阶段 JSON 解析失败自动重试 1 次
- [ ] 思考阶段输出缓存：相同输入直接复用思考结果
- [ ] 性能监控：记录每轮思考/检索/输出各阶段耗时和 token

**验收标准**：
- 首字延迟 < 2 秒
- 总成本 ≤ 单段式的 110%
- 思考阶段失败率 < 1%

## 九、风险与应对

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| 小模型思考质量不够，分析跑偏 | 中 | 输出阶段跟着错 | 先用 Flash 测试，如果不行换用主力模型的 mini 版；同时加校验 |
| 思考阶段 JSON 解析失败 | 低 | 本轮崩掉 | 自动重试 1 次；仍失败则降级为单段式（兜底） |
| 总延迟增加太多，玩家体感差 | 中 | 体验下降 | 配合流式输出，首字延迟反而更短 |
| 改造成本超预期 | 低 | 工期延长 | 分阶段实施，Phase 1 先跑通再迭代 |
| 小模型 + 大模型的费用反而更高 | 低 | 运营成本上升 | Phase 1 完了跑 A/B 测试，对比 token 用量再决定 |

## 十、关键设计决策总结

1. **选两段式而不是三段式**——检索穿插在中间同步执行，省一次调用开销，架构更简单
2. **思考用小模型、输出用大模型**——成本增加极小，质量提升明显
3. **思考输出严格 JSON**——结构化便于后端消费，也强制 AI 有条理地思考
4. **状态双重校验**——思考预判 + 输出更新，大幅降低漏更错更
5. **选项直接来自思考**——不再从正文里用正则抠，更准确也更有意义
6. **分三阶段落地**——先跑通骨架，再补全功能，最后优化体验，每一步都有可验证的产出
