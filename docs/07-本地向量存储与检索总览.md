# 本地向量存储与检索总览

> 本文档说明项目里两套本地向量系统的设计思路、部署要求和日常使用注意事项。
> 面向维护者，不需要机器学习背景也能看懂。

---

## 一、总览：项目里有两套向量系统

| | 世界书语义检索 | 长期记忆向量库 |
|---|---|---|
| 模块文件 | `semantic_index.py` | `local_vector_store.py` |
| 存的是什么 | **世界书**条目（NPC、武功、门派、物品、地点、剧情设定） | **游戏剧情**记忆（玩过的每一段经历） |
| 数据量 | 2221条 / 8818关键词 | 1581条（NPC记忆1038、单轮剧情493、章节摘要47、任务2、见闻1） |
| 起什么作用 | 玩家提到相关内容时，把设定资料递给AI | 让AI记得几百轮之前发生过什么 |
| 在上下文里叫 | L5语义层（叠加在关键词检索之上） | L4长期记忆 |
| 数据文件 | `data/semantic_vectors.npy`<br>`data/semantic_ids.json` | `data/local_memory_entries.jsonl`<br>`data/local_memory_vectors.npy` |
| 一次检索耗时 | 约40ms | 约20~30ms |

两套系统**互相独立、各管各的**，但用了同一个小模型：`BAAI/bge-small-zh-v1.5`（一个约100MB的中文语义模型，跑在CPU上，不花一分钱API费）。

**为什么要分两套？** 世界书是"设定资料"（静态，改了要重建索引），剧情记忆是"经历"（每轮都在增长）。数据性质不同，分开存储互不干扰。

## 二、共同的设计思路

### 2.1 向量是什么（一句话版）

把一段文字变成一串数字（512维向量），意思相近的文字，数字也相近。检索时把玩家的话也变成数字，找"数字最接近"的条目——所以"医书"能搜到"本草纲目"，哪怕字面完全不同。

### 2.2 为什么是两个独立模型实例

每个模块各自加载一份模型（各占约100~130MB内存）。这是**有意的设计取舍**：

- 世界书模块是老代码，早就在跑、经过测试
- 记忆本地化是新需求
- 各自独立一份实例，**谁都不用改谁**，出了问题互不影响

代价是内存多占一份。服务器内存紧张时见第六节的swap建议。

### 2.3 零API成本

所有向量计算都在本地CPU完成。不调用任何云端接口，不产生任何费用。这是从百炼云端迁移到本地的根本原因。

## 三、世界书语义检索（semantic_index.py）

### 3.1 设计思路

世界书原本只有**关键词检索**（L1~L4）：条目里登记了关键词，玩家输入命中关键词才召回。问题是有话不直说——玩家说"找个会治病的人"，关键词"大夫"根本没出现。

语义向量层（L5）叠加在关键词之上：

```
玩家输入 → 关键词检索（原有，精确命中）
        → 语义检索（新增，意思相近也算命中）
        → 两路结果按分数合并，去重后注入上下文
```

关键词是主力，语义是补充，**语义只在关键词没找全时补位**，所以分数权重可调（`SEMANTIC_SCORE_WEIGHT=2.0`）。

### 3.2 数据怎么存

- `semantic_vectors.npy`：所有条目的向量（一个大矩阵，2221行×512列）
- `semantic_ids.json`：行号和条目ID的对应表
- 世界书数据源（`data/` 下6个JSON）有改动时，索引会**增量更新**：新增的条目补算向量，删除的条目移除，没变的直接复用

### 3.3 安全降级

模型加载失败、缓存文件损坏、依赖缺失——任何一环出问题，世界书自动退回纯关键词检索，**游戏照常能玩**，只是召回少一些。控制台会打日志提示。

## 四、长期记忆向量库（local_vector_store.py）

### 4.1 设计思路

这套系统用来**替换百炼云端记忆服务**（原来每次读写都走API）。设计上做了一个关键决定：**接口和云端一模一样**。

`cloud_memory_v2.py` 末尾有个开关：

```ini
# .env
MEMORY_BACKEND=local   # local=本地向量库 / cloud=百炼云端（改后需重启）
```

开关拨到哪边，`main.py` 里的13个 `upload_*` 函数就走哪边。**主程序一行不用改**，随时可以切回云端。

### 4.2 记忆怎么写入（谁在存、存什么）

| 类别 | 什么时候存 | 存什么内容 |
|---|---|---|
| NPC记忆 | AI每轮调用工具时（状态/好感/记忆更新）+ 每50轮章末蒸馏 | 【某某的记忆】剧情节点，记忆内容 |
| 单轮剧情 | 每轮检测玩家输入，命中约100个武侠关键词（或超20字含动作词）才存 | 玩家行动 + 本轮剧情 |
| 章节摘要 | 每50轮后台AI生成 | 300~400字章回体摘要（唯一走AI生成的记忆） |
| 任务记录 | 任务完成时 | 任务经过总结 |
| 江湖见闻 | 每轮 | AI输出的【近期剧情记录】 |

### 4.3 防重复机制（重要）

每条记忆带唯一ID，**同ID再传自动跳过**：

- NPC记忆 → 记忆文本的MD5（同样的话不会存两遍）
- 单轮剧情 → 轮次号（每轮最多一条）
- 章节摘要 → 章节号（每章固定一条）

所以所有写入操作**幂等**，重复执行不会产生脏数据。迁移脚本也因此可以放心重跑。

### 4.4 存储文件说明

- `local_memory_entries.jsonl`：一行一条记忆（文本内容、分类、ID）——**人类可读，可以打开看**
- `local_memory_vectors.npy`：对应的向量矩阵——**两个文件按行序一一对应，绝对不能只改一个**

写入时攒够8条才落一次盘（减少磁盘IO），进程退出前强制落盘，不会丢。

### 4.5 新旧数据的一个已知差异

迁移过来的旧NPC记忆**不带**剧情节点时间戳；切换到本地后新写入的记忆都带（格式如`【胡一刀的记忆】1753年冬，腊月十五落马坡胡苗决战，……`），让AI知道这是什么时候的记忆。旧数据不补。

## 五、部署要求与步骤

### 5.1 服务器要求

| 项目 | 要求 |
|---|---|
| 系统 | Ubuntu 20.04+ |
| Python | 3.10 或 3.12（**不要3.13**，torch不兼容） |
| 内存 | 2GB以上；紧张的话务必加swap（见6.3） |
| 磁盘 | 额外500MB（模型+数据+缓存） |
| 网络 | 首次启动需联网下载模型（约100MB），之后离线可用 |

### 5.2 依赖安装

```bash
pip install sentence-transformers numpy
```

（会自动装上CPU版torch，体积较大属正常）

### 5.3 部署步骤（从云端切到本地记忆）

```bash
# 1. 上传文件：local_vector_store.py、cloud_memory_v2.py、migrate_cloud_to_local.py、web_server.py

# 2. 服务器上执行迁移（幂等，可重跑；约2分钟）
python migrate_cloud_to_local.py

# 3. 修改 .env
#    MEMORY_BACKEND=local

# 4. 重启服务（gunicorn）
```

迁移脚本会自动从本地数据源重放历史（NPC档案、交互日志、章节缓存），不需要从云端下载任何东西。跑完会打印各类条数和与云端ID的对齐率。

### 5.4 验证部署是否成功

打开网页看顶部状态栏：

- **世界书**：`✅ 世界书检索已就绪 · 2221条 | 语义✅ 2221条向量`
- **记忆**：`✅ 长期记忆已就绪 · 1581条（NPC记忆1038/单轮剧情493/…）`

刚启动的30秒内显示⏳加载中是正常的——状态接口发现模型没加载会自动在后台启动加载（自愈机制），半分钟内自己转✅，不需要手动干预，也不需要先跑游戏回合。

## 六、注意事项（日常维护必读）

### 6.1 改了 .env 必须重启

`MEMORY_BACKEND` 和 `SEMANTIC_MODEL` 都只在启动时读取一次，改完不重启不生效。

### 6.2 数据文件别手工编辑

- `local_memory_entries.jsonl` 和 `local_memory_vectors.npy` 行序一一对应，手工改一个不改另一个，检索结果会错乱
- 想清理数据，正确做法是两个文件一起删，然后重跑迁移脚本重建

### 6.3 内存紧张的服务器加swap

两个模型实例合计约250MB，加上游戏本体，小内存服务器（1GB）建议加1GB swap防止偶发OOM被系统杀进程：

```bash
sudo fallocate -l 1G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
# 持久化：echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

### 6.4 备份清单

需要备份的向量相关文件（都在 `data/` 下）：

| 文件 | 内容 | 丢了怎么办 |
|---|---|---|
| `local_memory_entries.jsonl` | 记忆正文 | 可从数据源重放重建 |
| `local_memory_vectors.npy` | 记忆向量 | 可由正文重算（几分钟） |
| `semantic_vectors.npy` | 世界书向量 | 可由世界书JSON重算 |
| `semantic_ids.json` | 世界书向量对应表 | 同上 |

正文文件比向量文件更重要——向量永远可以重算，正文不行（除非重跑迁移）。

### 6.5 gunicorn 多worker的行为

状态栏的两个✅由状态接口的自愈机制保证（首次查询触发后台加载），不依赖游戏回合。所以无论gunicorn怎么配（preload、多worker），打开网页半分钟内都会就绪。如果超过1分钟还是⏳，看服务日志里 `[本地记忆] 模型加载失败` 的报错原因（多半是依赖没装全或内存不足）。

### 6.6 切回云端随时可以

本地库不删云端数据。想切回百炼：`.env` 改 `MEMORY_BACKEND=cloud`，重启即可。两边各自独立积累，互不覆盖。

### 6.7 模型第一次下载慢怎么办

`sentence-transformers` 默认从 HuggingFace 下载，国内服务器可以设镜像：

```bash
export HF_ENDPOINT=https://hf-mirror.com
```

（写进服务的启动环境变量里，只需第一次生效）
